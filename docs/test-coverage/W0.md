# W0: 計測基盤とテストヘルパの整備

> テストカバレッジ改善ワークストリームの 1 つです。全体像は [README.md](./README.md) を参照してください。

## 前提

- **依存**: なし。**このワークストリームは W1〜W6 すべての前提**です。W1 はこのワークストリームの作業ブランチをベースに開始します。
- **ベースブランチ**: 統合ブランチ `claude/test-coverage-improvement-plan-x14ldp`。作業ブランチはこのベースから切られた状態でセッションが始まります（**Claude Code Web が自動で作成するため、自分で `git checkout -b` する必要はありません**）。
- **すべての Flutter/Dart コマンドに `fvm` を前置すること**（`.fvmrc` で Flutter バージョンを固定しているため）。
- **ファイルの作成・編集には Edit / Write ツールを使い、シェルの heredoc（`cat > file <<EOF`）は可能な限り使わないでください。** heredoc は Edit / Write で正しく書き込めない場合のみのフォールバックとします。
- **完了したら、ベースブランチを base とした PR を 1 本作成してください。** ワークストリームごとに個別にレビューします。
- 他ワークストリームの PR にはコメント・変更を行わないでください。

## 背景

このリポジトリにはカバレッジを計測する仕組みがなく（CI は `fvm flutter analyze` + `fvm flutter test` のみ）、テストを増やしても改善が定量的に追えません。また既存のテストヘルパ（`test/utils/`）は現行テストが必要とした最小限しか揃っておらず、W1〜W6 が同じヘルパを重複実装してしまう恐れがあります。

このワークストリームは **①カバレッジの計測と可視化 ②後続が共通で使うテストヘルパの用意** の 2 つを担当します。

## 作業一覧

### 1. `scripts/coverage.sh`（新規・実行権限付き）

既存の `scripts/*.sh`（`build_runner.sh`, `slang.sh` など）と同じ流儀で書いてください。

要件:

- `fvm flutter test --coverage` を実行する
- `lcov --remove coverage/lcov.info` で生成コード等を除外し、`coverage/lcov-filtered.info` を出力する。除外パターン:
  - `*.g.dart`
  - `*.freezed.dart`
  - `*.drift.dart`
  - `*.steps.dart`
  - `*.mocks.dart`
  - `lib/i18n/*`
  - `lib/firebase_options.dart`
  - `lib/routes.dart`（生成ルート定義が大半のため）
- `--ignore-errors unused` を付け、パターンが 1 つも一致しなくてもスクリプトが落ちないようにする
- 既定の出力は `lcov --summary` によるサマリ表示のみ
- `--html` 引数が渡されたときのみ `genhtml` で `coverage/html/` に HTML レポートを生成する
- `lcov` が未インストールの場合は、導入方法（`apt-get install lcov` / `brew install lcov`）を案内して非ゼロで終了する
- `set -euo pipefail` を付ける

### 2. `.gitignore`

`coverage/` を追加してください（現在未登録です）。既存の「Flutter/Dart/Pub related」セクションの近くが適切です。

### 3. `.github/workflows/test.yaml`

既存の `Test` ステップを拡張します。

- `Init Flutter SDK` の後に `sudo apt-get install -y lcov` を実行するステップを追加
- `Test` ステップの `run: fvm flutter test` を `run: ./scripts/coverage.sh` に置き換え
- `lcov --summary coverage/lcov-filtered.info` の出力を `$GITHUB_STEP_SUMMARY` に追記し、PR 画面から見えるようにする
- **しきい値による失敗はさせないこと**（今回はレポートのみ。ゲートは設けない方針）
- 既存の `if: ${{ !cancelled() && contains(fromJSON('["success", "failure"]'), steps.lint.outcome) }}` 条件はそのまま維持すること
- `Lint` ステップ（`fvm flutter analyze`）は変更しない

### 4. `test/utils/asset_data.dart` の拡充

**既存の `buildTestAssetData()` / `buildTestMaterial()` / `buildTestCharacter()` のシグネチャは後方互換を保つこと**（引数の追加はすべて任意引数で行う）。既存テストが壊れてはいけません。

追加するもの:

| 追加 | 内容 |
|---|---|
| `buildTestWeapon({String id, int rarity, MaterialDefinitions? materials, ...})` | `buildTestCharacter()` と同じ流儀の `Weapon` ビルダー |
| `buildTestAssetData()` への任意引数追加 | `Map<String, Weapon> weapons`, `IngredientConfigurations? characterIngredients`, `IngredientConfigurations? weaponIngredients`, `List<DropRateEntry> dropRates`, `Map<MaterialId, List<CharacterId>> specialCharactersUsingMaterials` |
| `buildIngredientConfigurations({required int rarity, required Purpose purpose, required Map<int, List<Ingredient>> levels, List<ExpItem> expItems})` | **現在 `test/unit/material_calculator_test.dart` 内にプライベート関数 `_buildIngredientConf` として存在するものをここへ移す。** 移動後は `material_calculator_test.dart` からこのヘルパを呼ぶよう置き換え、重複を消すこと |

### 5. `test/utils/db.dart`（新規）

| 追加 | 内容 |
|---|---|
| `AppDatabase createTestDatabase()` | `AppDatabase(NativeDatabase.memory())` の薄いラッパ |
| ブックマーク投入ヘルパ | `MaterialBookmarkInsertable` を定型生成する関数（`characterId` / `materialId` / `purposeType` / `upperLevel` / `quantity` を任意引数で受ける） |

W3 と W4 がこれを多用します。

### 6. `test/utils/provider_container.dart`（新規）

| 追加 | 内容 |
|---|---|
| `ProviderContainer createTestContainer({AssetData? assetData, AppDatabase? db, List<Override> overrides})` | `assetDataProvider` / `appDatabaseProvider` / `shouldHideImagesProvider` の定型 override をまとめる。内部で `addTearDown(container.dispose)` を呼ぶこと |

`assetDataProvider` の override の書き方は `test/widget/bookmark_furnishing_sets_tab_test.dart` を参照してください（`requireValue` が呼ばれるため同期的に返す必要があります）。
`ProviderContainer.test(...)` の使い方は `test/unit/resin_provider_test.dart` を参照してください。

W4 と W5 がこれを多用します。


CI の変更が正しいかは、プッシュ後に GitHub Actions の `Test & Lint` ワークフローが緑になり、ジョブサマリにカバレッジ表が出ていることで確認してください。

コミットは意味単位で分けてください（例: 計測スクリプト / CI / テストヘルパ）。

### PR の作成

作業ブランチに push したら、**ベースブランチ（統合ブランチ `claude/test-coverage-improvement-plan-x14ldp`）を base にして PR を 1 本作成**してください。

- **draft にしないでください。** draft では自動レビュー（`.github/workflows/claude-code-review.yml`）が動きません。
- タイトルは `test: W0 ...` のように、どのワークストリームかがわかる形にしてください。
- 本文には次を記載してください: カバレッジ計測の仕組み（除外パターンの根拠を含む）、CI の変更内容、追加したテストヘルパとその用途、**計測したベースラインのカバレッジ率**。
- リポジトリに PR テンプレートはありません。本文は通常どおり記述してください。
- PR 作成後、**CI（`Test & Lint`）が緑になるまで**が完了条件です。CI ではカバレッジのサマリがジョブサマリに出ることも確認してください。
- **bot によるレビューコメント（`.github/workflows/claude-code-review.yml` の自動レビューなど）には、ユーザーから明示的な指示があるまで対応しないでください。** 修正・返信・resolve のいずれも行わず、そのまま残してください。
- **W1 はこのブランチをベースに開始します。** PR のマージを待つ必要はありませんが、レビュー指摘でこのブランチを更新した場合は、W1 以降が取り込む必要があることを念頭に置いてください。
- **レビューコメントへの対応を指示されたら、修正 → 該当レビューコメントへの返信 → スレッドの resolve → push の順**で行ってください。先に push すると、どの指摘に対する変更なのかがレビュアーから追えなくなります。
- **コンフリクト解決など、内容を変更しない push の後は、コードレビューのワークフローが Actions に現れるのを待ってからキャンセルしてください。** 実質的な差分がない変更に自動レビューを走らせないためです。ワークフローは push 直後には現れないことがあるので、現れるまで待ってからキャンセルします。
- **作業完了後、その PR にサブスクライブされていないことを確認してください。** サブスクライブが残っていると、以後の PR の動きでセッションが起動し続けます。残っている場合は解除してください。
